Project — Delhivery Last-Mile Delay Intelligence Pipeline
Delhivery is India's largest integrated logistics provider, express parcel, freight, warehousing, cross-border shipping many more delivery services
Every file uses python's free libraries (pandas, NumPy, scikit-learn, joblib). The data is generated with script generate_data.py
The real data records are not used. Moner is Indian Rupees (INR)

The given data has three open questions:
1. How long will a parcel really take?
2. Which parcels will miss their promise?
3. Which hubs need which playbook?

The given repository answers these three questions in one connected pipeline: Part A prepares the data for all of the below parts and are reused by 
Part A and by the scoring script.
The cleaning and feature functions live once in src/shipment_prep.py.
how long will a parcel take (Part B), which parcels will miss their promise (Part C), and which hubs need which playbook (Part D).  

How to run
From a fresh clone of the main branch (Python 3.11 or newer):

pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py

The above sequence of file execution should be followed because each one reads files written by an earlier one. 
models/delay_model.pkl is regenerated by running python package_model.py. 
The pickle loads reliably only on the scikit-learn version mentioned in requirements.txt 
(scikit-learn 1.8.0); if your installed version is not same, re-run package_model.py instead of loading the committed pickle. 
Every random step uses random_state=42 (the data generator uses its own fixed seeds), so repeated runs give the same files.

Data findings
The raw export had 1,224 rows. After removing 24 exact duplicates, 1,200 shipments remain, of which 278 are delayed (delay rate 0.2317). These figures are in outputs/part_a_checks.csv; the tables below are in outputs/part_a_delay_by_group.csv and outputs/part_a_correlations.csv.

Service type. 
Express parcels are delayed most often: 119 of 243, a delay rate of 0.4897. Standard is 0.2056 and Economy only 0.0857. 
Express has the tightest promise (36 hours), so even small mismanagement turns into a delayed delivery.

Hub tier. The delay rate climbs steeply with tier: 0.0400 for Tier 1, 0.2150 for Tier 2 and 0.4400 for Tier 3.

Distance. The delay rate rises sharply with distance: 0.0219 for 0-200 km, 0.1368 for 201-400 km, 0.4364 for 401-600 km and 0.8523 for
601+ km. Mean delivery hours rise from 46.7559 to 72.2608 over the same bands. 

Strongest correlations with delivery_hours 
(ranked by absolute value, excluding delivery_hours itself): promised_hours +0.8372, distance_km +0.4013 and n_stops +0.3247.
 Next are hub_daily_capacity at -0.3237 and hub_tier at +0.3175. Longer promises, longer lanes and more stops all mean more hours; 
 bigger-capacity hubs are faster.
Why declared_value_inr was log-transformed. On the median-filled column the mean is INR 1,533.0542 but the median is INR 1,121.5, 
so a few very expensive parcels pull the mean up (right skew); after the natural log the mean (7.0277) and the median (7.0224) 
almost coincide, giving a symmetric feature.

Model results (regression)
Split: 840 training, 180 validation, 180 test rows. The scaler was fitted on training rows only, the scaled test rows give 0.2187 
(part_b_checks.csv), which proves the scaler did not see the test rows.

Linear regression proved to be best with validation RMSE 4.8912 hours (R² 0.9313). Gradient boosting was almost identical (RMSE 4.9165, R² 0.9306), 
then random forest (5.5095, R² 0.9128) and the decision tree (6.2796, R² 0.8867).

Bias :  Depth 1 is high bias: train RMSE 11.6334 and validation RMSE 12.1324
Variance: Depths 12 and unlimited are high variance: unlimited depth fits the training set perfectly (train RMSE 0.0) but validation 
RMSE is 7.8368
Validation error is lowest at depth 6 (RMSE 6.2796, gap 1.5682), which is the depth used for the decision tree. Depth 6 is 5.8528 hours better 
than depth 1.

Learning rate (part_b_gb_learning_rate.csv). 0.1 is best (validation R² 0.9306). 
With 0.01 the ensemble is too slow and underfits. 
With 1.0 each tree's correction is applied in full, so the ensemble overshoots and chases noise.

Cross-validation : Gradient boosting: mean R² 0.9353 (std 0.0045). Gradient Boosting should be used.

Model results (classification):
Stratified split gives 840 / 180 / 180 rows with 195 / 42 / 41 delayed parcels.
Noise columns : The top seven are distance_km, hub_tier, hub_daily_capacity, n_stops, promised_hours, rain_flag and sale_event_flag.
Selecting k : k=5 drops real signal columns, and larger k adds noise columns back.Validation F1 is 0.6988 for k=5.

Tuning (part_c_tuning.csv). The final configuration is the default forest (n_estimators 100, no depth limit, min_samples_leaf 1) on k=7 features.
real shipments will be messier and the scores here are likely optimistic.

Alert threshold : The highest threshold meeting the rule is 0.5.

Operations recommendation
Alert threshold. Flag a parcel when its delay probability is at least 0.5. On the test rows, about 7 of every 10 flagged parcels are really delayed (precision 0.6889) and about 8 of every 10 delayed parcels are caught
New parcels. Of the 48 new parcels in new_shipment_actions.csv, 8 are flagged; The remaining 40 need no action.

Production plan
(a) Production-readiness characteristics mapped to repository items

Accuracy: held-out validation and test metrics in part_b_metrics.csv and part_c_final_test.csv, with the blind baseline for comparison.
Reliability: clean_shipments handles duplicates, casing, missing values, the 999 kg sentinel and the unknown payment mode; predict_delay.py asserts no missing feature values.
Reproducibility: pinned requirements.txt, committed generate_data.py, fixed random_state=42, and the run order in "How to run".
Performance (speed): the model scores a whole batch in one predict_proba call and the RandomForest with seven selected inputs is small enough to run inside the scoring script on demand.
Maintainability: one shared module src/shipment_prep.py, one script per Part, and constants (FEATURES, PROMISED_HOURS) defined once.
Consistency: training and prediction use the same clean_shipments and build_features, with the stored medians in models/impute_values.csv and the column order in models/feature_order.csv.
Monitorability: new_shipment_actions.csv stores the delay probability, flag, segment and action for every parcel, so each can be compared with the real outcome later.

Limitations
1. The data is synthetic:real shipments will be messier and the scores here are likely optimistic.
2. The regression winner (linear regression) and the model I recommend shipping (gradient boosting) differ; only the Gradient Bossting was scored on the test rows.
3. The packaged classifier is fitted on the 840 training rows only (not training plus validation)
